# 故障排除 { #troubleshooting }

在查看下面的条目之前，先打开**管理 → 状态检查**。它会测试 DNS、缓存可达性，以及近期下载是否用到了缓存，通常能直接指出问题所在。

### 日志没有被处理

1. 在**管理 → 日志与缓存 → 日志处理**中检查日志路径。
2. 确认你的数据卷挂载与 `LanCache__LogPath` 一致。
3. 在同一页面的**操作**菜单中选择**全部处理**。
4. 查看容器日志：`docker logs lancache-manager`。

### Web 界面显示"无日志源"（但日志文件确实存在）

把 `LanCache__LogPath` 指向存放 `access.log` 的目录（例如 `/logs`）；完整文件路径 `/logs/access.log` 也可以，因为 LANCache Manager 总是读取该目录下名为 `access.log` 的文件。使用其他文件名的日志不会被读取。请确认：

1. 你的数据卷已把宿主机的日志目录挂载进容器（例如 `- /host/path/lancache/logs:/logs`）。
2. `LanCache__LogPath` 指向该*容器内*路径下的文件（`/logs/access.log`）。
3. 该文件在容器内可读：`docker exec -it lancache-manager cat /logs/access.log | head`。

网络共享（NFS/SMB）没有问题。`ls -la` 输出末尾的 `+`（例如 `-rw-r--r--+`）是 NFS 的 ACL 标记。它**不会**阻止读取。如果 `cat` 能打印出文件内容，那问题就不在权限，应该检查的是所配置的路径。

### 仪表板没有显示缓存大小 / 磁盘占用

`LanCache__CachePath` 必须指向**直接包含哈希缓存文件夹**（名称形如 `00`、`1a`、`ff`）的目录，而不是它的上一级。

标准的 lancache（monolithic）布局会把内容嵌套在下一层。如果你把缓存数据目录挂载到 `/cache`，实际的哈希文件夹通常位于 `/cache/cache`——这时应设置 `LanCache__CachePath=/cache/cache`。如果指向的层级过高，仪表板会显示这个驱动器，但报告的缓存用量为零。网络挂载（NFS/SMB）的缓存行为相同。

检查该路径下有什么：

```bash
docker exec -it lancache-manager ls /cache
# 你应该看到哈希文件夹（00、1a……ff），而不是单个 "cache" 文件夹
```

### 游戏没有被识别

**Steam：**

1. 刷新映射：进入**管理 → 计划任务**，找到 **Steam 游戏映射** 那一行，点击**立即运行**（行尾的播放图标）。
2. 为你关心的任何私有 depot 添加自定义映射。
3. 重新导入历史记录：在**日志与缓存**中，从**日志处理**卡片的**操作**菜单选择**重新定位**，把读取位置移回起点，再次处理。已处理过的条目会自动跳过，所以重新处理是安全的。

**Epic：**

1. 在**管理 → 集成**中选择**使用 Epic Games 登录**。
2. 进入**管理 → 计划任务**，找到 **Epic 游戏映射** 那一行，点击**立即运行**。映射服务会查询 Epic API，识别你缓存中的内容。
3. 游戏名称和封面图会自动下载。

### 丢失 API 密钥

```bash
# 如果 /data 是绑定挂载（默认的 docker-compose.yml 就是这样），可以直接在主机上读取
cat ./data/security/api_key.txt

# 在任何地方都可用：直接从容器内部读取（命名卷同样适用）
docker exec lancache-manager cat /data/security/api_key.txt
```

在 Windows 的 Git Bash 中，请在 `docker exec` 命令前加上 `MSYS_NO_PATHCONV=1`（即 `MSYS_NO_PATHCONV=1 docker exec lancache-manager cat /data/security/api_key.txt`），否则路径会被改写成本地 Windows 路径。

之后的容器重启只打印文件路径和一段短提示，不会打印完整密钥。完整密钥仅在首次创建或轮换后写入日志。

要轮换密钥，停止容器，删除 `./data/security/api_key.txt`，然后重新启动。

### 忘记主管理员密码

无需删除数据库或账号即可重置密码。在主机上运行 `./data/scripts/reset-main-admin-password.sh`。其他容器名称、Unraid 和源码安装见[密码恢复](password-recovery.md)。

### 权限问题

确保 `PUID` 和 `PGID` 与你的缓存和日志文件所有者一致：

```bash
ls -n /path/to/cache
```

### 预填充无法运行

五个平台的排查清单是一样的。按顺序检查：

1. 确认 Docker 套接字已挂载。
2. 确认你已在 lancache-manager 中以**主要**或**账户**身份登录。
3. 查看容器日志中的网络诊断块（`═══ PREFILL CONTAINER NETWORK DIAGNOSTICS ═══`）——它会告诉你容器是否有网络，以及 CDN 域名解析到了哪里。
4. **预填充容器内没有互联网。** 容器无法连接到平台服务器。常见修复方法：
   - 设置 `Prefill__NetworkMode=bridge`（适用于大多数环境）。
   - 确认你的 Docker 网络有出站互联网。
   - 检查防火墙的出站流量规则。
5. **下载失败或中途报错。** 常见原因是容器无法把 CDN 域名解析到你的缓存。最可靠的修复是设置 `Prefill__LancacheIp=<你的缓存 IP>`——它会为 CDN 流量完全绕开 DNS。完整决策表（以及 `LancacheDnsIp`/`NetworkMode` 各自的作用）见[网络设置](prefill.md#prefill-network)。
6. **IPv6 流量绕过了 DNS。** 如果你的网络启用了 IPv6，查询可能会绕过 `lancache-dns`。LANCache Manager 会在 bridge 模式的预填充容器内禁用 IPv6 来防止这种情况；host 网络模式下 Docker 不允许这样做，所以 host 模式的容器需要在网络层面另行处理 IPv6。
7. **Epic 登录无法完成。** 打开 Epic 的登录页并在那里登录，然后把授权码粘贴到 LANCache Manager。登录保存在预填充容器里。当**重启后**设置为保留时，持久容器可以在 LANCache Manager 重启后仍然保持登录。临时会话以未登录状态开始。

查找 `lancache-dns` 的 IP：

```bash
docker inspect lancache-dns | grep IPAddress
```

### 计划预填充"跳过"了某些服务

这是[计划预填充](prefill.md#scheduled-prefill)的正常设计行为。计划运行只使用已经在运行的容器；Steam、Epic 和 Xbox 还必须已登录。

解决方法：

1. 在计划预填充卡片上，点击该服务的**启动**。
2. Steam、Epic 或 Xbox 需要点击**管理**并登录。

下一次运行就会包含它。无论哪种情况，计划都会保持其间隔。只有在没有任何服务运行时，本次运行才会报告为未成功。

### 预填充后命中率看起来比预期低

通常没有问题——这个数字把预填充本身也算了进去。仪表板的命中率是按字节加权统计所有接触过缓存的客户端得出的，包括预填充容器本身（[Prometheus](prometheus-metrics.md) 的 `lancache_service_hit_ratio` 指标也是同样的混合方式）。

在空缓存上，一次预填充运行接近 100% 未命中，随后的安装接近 100% 命中。两者合起来，单个游戏大致会拉平到 50% 左右。每次重复安装都会把这个数字推向 66%、75% 甚至更高，因为未命中的字节数是固定的基数，而每次安装都会给总数增加更多命中字节。

想按客户端隐藏预填充流量，先找到守护进程对应的客户端：

- 在缓存机器上使用 host 网络时，它显示为容器所连接的缓存地址，也就是缓存机器自己的地址。
- 在 bridge 模式下，缓存看到的是容器所加入的 Docker 网络的网关地址。

然后任选其一：

| 方式 | 效果 |
|---|---|
| 在下载或仪表板的客户端筛选器中过滤掉它 | 从视图中隐藏它的流量，不改变数据 |
| 在**管理 → 客户端**的客户端排除中加入它 | 同时把它排除在 [`/metrics`](prometheus-metrics.md) 之外 |
| 在**管理 → 客户端**的客户端排除中添加一条**预填充流量**规则 | 把预填充运行排除在各项数字之外，可针对任意地址或单个客户端。无需知道客户端地址。见[预填充流量规则](#prefill-traffic-rules)。 |

想查看某次具体安装的真实命中率，可以把下载页切换到**复古**视图，打开设置面板，让**显示**下的**按游戏分组**保持未勾选，再查看该客户端自己的那一行，或者在 `access.log` 中按其 IP 进行 grep。管理器只统计 nginx `upstream_cache_status` 中字面意义上的 `HIT`/`MISS`，因此结果始终与手动统计日志的结果一致。


即使是一次干净的安装，出现一些真实的未命中也是正常的：

- 预填充守护进程默认只抓取 Windows/x64/英语的 depot
- 之前一次没有使用 `--force` 而被中断的运行会留下缺口
- 绕过 `lancache-dns` 的 HTTPS/IPv6 流量永远不会经过缓存

#### 预填充流量规则 { #prefill-traffic-rules }

**管理 → 客户端**页面**客户端排除**中的每条规则，都作用于**全部流量**或**预填充流量**。预填充规则只匹配管理器标记为来自预填充运行的下载。点击**保存更改**之前，什么都不会改变。

| 规则字段 | 可选项 |
|---|---|
| 地址 | 单个客户端地址，或**任意地址**（由**添加预填充规则**创建）。没有地址的规则只能是预填充规则。 |
| 服务 | **全部服务**，或 Steam、Epic Games、Xbox、Battle.net 和 Riot 中的任意几项。只有预填充规则可以选择服务。 |
| 模式 | **隐藏**或**仅统计**，与全部流量规则的两种模式相同。 |

预填充规则按下表处理它匹配到的下载：

| 模式 | 排除 | 保留 |
|---|---|---|
| **隐藏** | 总服务量、节省的带宽、命中率、客户端数量、进行中的下载、下载列表及其 24 小时历史，以及 `/metrics` | **新增缓存量** |
| **仅统计** | 仪表板各项数字和 `/metrics` | 下载列表、实时速度和**新增缓存量** |

保存预填充规则后，**总服务量**不再等于**节省量**加**新增缓存量**。

- 标记从保存第一条预填充规则时开始。在此之前的预填充运行仍会计入。
- 某个地址有预填充规则时，仍可以为同一地址添加全部流量规则。
- 管理器会学习预填充容器在其加入的每个网络中的自有地址，并把同一服务、运行期间来自该地址的下载标记为预填充。
- 使用主机网络的容器没有自己的地址，所以管理器会标记来自它所连接的缓存地址的下载。缓存运行在同一台机器上时这种方式有效。
- 如果使用主机网络的容器连接的是另一台机器上的缓存，或缓存看到的流量来自共享地址（例如 Docker 桥接网关（NAT）或代理），这些预填充流量不会被标记。任何预填充规则都无法隐藏这些下载，它们仍会计入。

### 调试日志

在路径自动检测失败、预填充容器无法启动、数据卷挂载看起来不对，或者你使用的是不常见的平台时，可以开启详细的平台日志：

```yaml
environment:
  - Logging__LogLevel__LancacheManager.Infrastructure.Platform=Debug
```

你会得到以下方面的额外细节：

- 路径解析（容器路径 vs 主机路径）
- 文件系统操作与权限检查
- Docker 套接字通信与容器检测
- 数据卷挂载检测
- Linux/Windows 平台差异

使用方法：添加该变量，用 `docker compose up -d` 重启，复现问题，然后查看 `docker logs lancache-manager`。排查完成后移除该变量——它的日志量很大。
